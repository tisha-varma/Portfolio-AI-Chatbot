6.1 RAZORFLOW AI - Agentic Commerce and Payments Platform
---------------------------------------------------------------------
Repository: https://github.com/tisha-varma/RazorFlow-AI
Built solo for the Razorpay Buildathon, Track 01: AI Growth and Agentic
Commerce. Public repository, master branch.
LinkedIn post: about 88 reactions and about 4,900 impressions.

Idea: an AI shopping agent that understands a natural-language request,
discovers products through an AI-readable merchant catalog, recommends
and upsells, but never spends money without explicit user approval. The
AI is good at understanding people but unreliable with money, so every
money decision is made by ordinary deterministic backend code plus a
human approval. "AI recommends, human approves, system verifies."
Architecture: AI -> Policy Engine -> User Approval -> Razorpay ->
Payment Verification -> Order.

Key numbers: 181 automated pytest tests; 12 states in the session state
machine (SessionState); about 40 REST endpoints; 10 API routers; 13
database tables.

Stack: Python, FastAPI, SQLAlchemy, Pydantic, SQLite (foreign keys on),
Razorpay API in test mode with the official Python SDK, pytest; an LLM
served through Groq with Gemini and a local Ollama model also supported;
Next.js/TypeScript frontend with Tailwind CSS. Prices are stored as
integer paise (Rs 1 = 100 paise) to avoid floating-point errors.

Database tables: Merchant, Product, ProductVariant, CommercePolicy,
Cart, CartItem, Approval, Order, OrderItem, RazorpayPayment, AuditEvent,
AIInteraction, SessionStateEvent.

Purchase flow, step by step:
1. POST /api/agent/chat: logs USER_INTENT_RECEIVED, sets the session
   state to DISCOVERING, loads chat history (rebuilt from the
   AIInteraction table after a server restart), and adds a live cart
   snapshot to the LLM context.
2. Tool-calling loop (up to 4 rounds): the LLM can request tools for
   searching products, getting a product, checking stock, finding
   related products, creating a cart, adding/removing/updating cart
   items and initiating checkout. The LLM only requests tools; backend
   code runs them. The LLM never passes a price or session id; the
   server supplies both.
3. Cart: CartService.add_item reads the price from the database and
   snapshots it on the cart line (unit_price_paise). Totals are integer
   sums computed in Python. Related products (for example socks with
   shoes) are attached as upsell suggestions and logged as
   UPSELL_OFFERED. The policy verdict returns with every cart change.
4. Policy engine (check_purchase_policy), checked in order: the cart
   exists and is not empty; it has at least one real (non-upsell) item;
   the total is within the minimum and maximum transaction (default
   maximum Rs 5,000); the per-item quantity cap (5); paid spending in
   the session plus the cart is within the session limit (Rs 10,000);
   the upsell portion is within its cap (Rs 2,000). Only paid orders
   count toward the session limit, so a failed payment does not use up
   budget.
5. initiate_checkout does not pay. It creates a pending Approval row
   with a random single-use token and a frozen copy of the policy, and
   moves the state to AWAITING_APPROVAL. A pending approval for the same
   amount is reused; if the cart changed, the old approval is marked
   expired.
6. POST /api/checkout/approve: constant-time token comparison; the token
   is deleted so the request cannot be replayed; the policy is re-run;
   the state transition is checked; the approval is marked approved and
   PAYMENT_APPROVED is logged. No LLM tool can perform this step.
7. /api/payment/create-order: requires an approved approval; a
   stale-amount check recomputes the cart total and returns HTTP 409 if
   it differs from the approved amount; the policy is re-checked; the
   server creates the Razorpay order for the server-calculated amount
   (the browser never sends an amount); saves the Order and
   RazorpayPayment rows and logs PAYMENT_ORDER_CREATED.
8. The browser opens Razorpay's checkout.js popup using only the public
   key id.
9. Payment is confirmed in three independent ways: (a) browser
   verification, where the server finds the order by the Razorpay order
   id stored in its own database and recomputes the HMAC signature; (b)
   a webhook at /api/payment/webhook for payment.captured and
   payment.failed, with the signature checked on the raw body, events
   older than 5 minutes ignored and duplicate payment ids skipped; (c)
   status polling at /api/payment/status/{id} for about 30 seconds.
10. _mark_order_paid sets the order to paid, empties the cart, moves the
    state to ORDER_CONFIRMED and writes audit events. The merchant
    dashboard reads the same tables.

Other components:
- Agent behaviour: fixed (non-LLM) replies for sensitive messages such as
  "Approval completed" and "Payment successful"; pattern-matched "show me
  more options" without an LLM call; provider fallback across multiple
  rotating Groq API keys.
- State machine: includes IDLE, DISCOVERING, RECOMMENDING,
  CART_BUILDING, UPSELLING, POLICY_CHECK, AWAITING_APPROVAL,
  PAYMENT_PENDING, PAYMENT_SUCCESS, PAYMENT_FAILED (retry returns to
  PAYMENT_PENDING) and ORDER_CONFIRMED; 12 states in total. Illegal
  transitions return HTTP 409. State lives in server memory and
  recover_session_state rebuilds it from the database after a restart.
- Audit log: every important event is an AuditEvent row whose hash is
  SHA-256(previous hash + event type + event data + actor + session id).
  GET /api/audit/verify reports where the chain breaks, and the
  dashboard shows a "chain intact" badge.
- Merchant dashboard: revenue, average order value, AI conversion (paid
  orders divided by AI sessions), upsell revenue, and a "with AI vs
  without AI" comparison. Orders are prefixed RF- (live test purchases),
  HIST- (seeded history) or DEMO- (scripted demos); only RF- orders count
  as live.
- /.well-known/ai-commerce.json: a public machine-readable description
  of the shop (catalog, limits, purchase flow) for other AI agents.
- Frontend pages: landing, buyer (chat, cart, approval card), merchant
  (dashboard, audit table) and setup (edit the policy). The session id is
  kept in localStorage and the approval card polls about every 2.5
  seconds.
- Protection: rate limit of 120 requests per minute per IP on payment
  and checkout routes; secrets only in .env; the Razorpay secret key is
  never sent to the browser; HTTP 409/403 errors for stale, replayed or
  invalid actions.
- Failure handling: a failed payment marks the order failed, logs the
  event, uses no budget and allows a new Razorpay order on retry under
  the same approval; a payment confirmed after the user closes the popup
  is picked up by the webhook and status polling; duplicate webhook
  events are ignored.
- Demo scenario in the README: "marathon shoes under Rs 5,000" ->
  recommend RunPro Sprint (Rs 4,499) -> upsell socks (Rs 499) -> cart
  of Rs 4,998 passes the policy -> approve -> Razorpay test checkout ->
  order -> audit trail -> merchant dashboard; plus a failure scenario
  with no duplicate charge.

Current limitations: no user authentication yet; session state is held
in memory so only one server process can run; LLM calls are blocking;
the audit chain is tamper-evident rather than unbreakable (timestamps
and reason text are not hashed, there is no secret key, and concurrent
writes can fork it); the "without AI" revenue figure is derived by
subtracting upsell items, not from a controlled experiment.

6.3 AMAZON VIDEO GAMES EXPLAINABLE RECOMMENDATION SYSTEM
---------------------------------------------------------------------
Repository: https://github.com/tisha-varma/Amazon-Recommendation-System
Live demo: https://amazon-recommendation-system-games.streamlit.app/
Tagline: Comparing SVD, KNN, NMF with Explainable AI Recommendations.
Repository: public, 16 commits, MIT license badge. LinkedIn post: 481
impressions.
Stack: Python 3.12, scikit-surprise 1.1.5, pandas, scikit-learn, numpy,
matplotlib, seaborn, Streamlit, Hugging Face datasets.

Idea: compare three collaborative-filtering algorithms on real Amazon
data and give a human-readable reason for every recommendation.

Data: Amazon Reviews 2023, Video Games category. 1,000,000 raw reviews
sampled (streamed from 2.8M total, no full download), filtered to
128,687 interactions from 14,839 users and 2,206 items; 99.61% sparse;
8.7 ratings per user and 58.3 ratings per item on average. Filtering
iteratively removes users with fewer than 5 ratings and items with fewer
than 20 ratings until stable (22 iterations).
Split: temporal 80% train / 10% validation / 10% test, so the model never
trains on the future.
Models: SVD (100 factors, 20 epochs), item-based KNN (cosine, 40
neighbours), NMF (50 factors, 50 epochs).
Metrics: RMSE, Precision@K, Recall@K, NDCG@K; a "liked" item is a
rating of 4 or higher.

Results (from the repository README):
  Model | RMSE   | P@5    | P@10   | R@10   | NDCG@10
  SVD   | 1.1911 | 0.3481 | 0.1954 | 0.7443 | 0.8081
  KNN   | 1.2527 | 0.3538 | 0.2004 | 0.7633 | 0.8053
  NMF   | 1.2760 | 0.3514 | 0.1996 | 0.7642 | 0.8046
SVD is best on RMSE and NDCG@10, KNN on Precision@5 and @10, NMF on
Recall@10. The best rating predictor is not always the best
recommender.

Explainability:
- KNN: true explanation by tracing which of the user's highly rated
  items are neighbours of the recommended item.
- SVD and NMF: approximate explanation through co-purchase patterns
  (users who rated this item highly also rated X highly), since latent
  factors are not human-readable.
Features: dark-themed Streamlit app with personalised recommendations,
cold-start handling (fallback to popular items), user history
visualisation and live algorithm comparison.
Exploratory findings: 64% of reviews are 5-star; the top 10% of items
receive over 60% of ratings; the matrix is 3.21% filled; review volume
peaked in 2018-2020.
Stated limitations: optimistic rating bias, cold start, a limited item
pool, approximate explanations for SVD and NMF.
Pipeline: preprocess.py -> train.py -> evaluate.py / explain.py ->
recommend.py -> app/streamlit_app.py.

6.4 PHARMAMATE - Pharmacist's Assistant
---------------------------------------------------------------------
Repository: https://github.com/tisha-varma/PharmaMate
Google Girl Hackathon 2025 finalist. Built solo.
Public repository, 7 commits; README screenshots dated 25-26 Feb 2025.
Stack: Python, Tkinter GUI, Pandas, Pillow, Google Generative AI
(Gemini API).

What it does: a pharmacist's assistant that matches orders against
handwritten prescriptions, creates the order, and offers a
symptom-to-possible-condition assistant.
- The user uploads a prescription image. It is sent directly to Gemini
  (gemini-2.0-pro-exp-02-05, via the google.generativeai library) as
  image bytes, so no separate OCR library is used.
- Medicine names are extracted from Gemini's reply with a regular
  expression and checked against a pandas-backed inventory file
  (medicine_database.csv).
- If a medicine is unavailable, a second Gemini call suggests 3
  alternatives and the first one found in the inventory is used.
- Price, frequency and special instructions come from the inventory
  file; the final order with total cost can be saved as a text file.
- Processing runs in a background thread so the Tkinter interface stays
  responsive. The Gemini API key is configured by pasting it into
  main.py, as described in the README.
- The symptom module (systoms.py) asks for symptoms through an interface
  and suggests a possible condition.

6.5 AI STUDY BUDDY
---------------------------------------------------------------------
Repository: https://github.com/tisha-varma/AI-study-Buddy
A local multi-agent learning assistant built with CrewAI, Ollama
(Mistral) and Streamlit. It runs fully on the user's machine (private,
zero-cost, offline inference). Python 3.12+; setup uses
`ollama pull mistral` with CrewAI pointed at the local Ollama endpoint

Three agents run in a strict sequence:

  2/3.

personalised feedback. Interfaces: Streamlit web app (app.py) and a
command-line tool (main.py), both over the same backend logic.
Public repository, 3 commits, demo video in the README.
